# Uncovering Systematic Blind Spots in Graph Database Testing through Integration and Process-Level Analysis — Highlights

Source: arXiv 2611.07754v1 (LaTeX source, abstract, §1–§9, Tables 1–7, Figs. 1–10).

**Task.** Run the test capabilities of eight published graph-database testing methods together on one platform, study what they report and why, and turn the findings into an integrated platform (GraphWeave) that makes testing a new graph database practical with modest computational and human effort (abstract, §1).

**Challenge.**
- Each graph-database testing method checks a different aspect of correctness and exposes a different class of defect, but no prior work has run them together, and their combined behaviour is unknown (§1).
- Methods are judged by the real bugs they find, not by useless reports or tests that can never fail; those decide whether a developer can afford to act on the output (abstract, §1).
- Differential testing has false negatives when several systems share a defect, and false positives where the language standard leaves semantics under-specified and systems resolve it in different, legitimate ways (§2.1).
- The Cypher specification leaves pattern-matching semantics (edge reuse, how many times a match is counted, where uniqueness resets) underspecified, and GQL makes path semantics user-selectable (§2.2).
- Query optimizers are built to erase surface differences between equivalent queries, which is exactly the difference equivalence-based metamorphic tests rely on (§2.3).

**Solution.** A unified testing model in which every method varies one argument of `execute(S, Q, t)` (graph-derived methods vary the graph state S, statement-metamorphic methods the query Q, differential testing the target system t); a shared engine runs all capabilities, a per-target adapter holds all system-specific logic, and every run records *process-level data* (how each state and query was derived, the execution plans, the semantic preconditions each relation relies on) (§3, Algorithm 1).
- **Integrated methods (Table 1):** graph-derived Gamera (2023), GSlicer (2025); statement metamorphic GDBMeter (2023), Gamera (2023), GraphGenie (2024), GraspDB (2024), GRev (2024), Dinkel (2026); differential GDsmith (2023).
- **Postprocessing pipeline (§5.1–5.3, Fig. 9):** standardized artifacts → rule-based issue gate (matches a known-issue library) → clustering by capability label refined with report embeddings → multi-agent analysis. A coordinator agent dispatches three sub-agents (all Claude Code with `claude-sonnet-4-6`): a cluster-splitting agent (compares the medoid with the farthest outlier and splits a heterogeneous cluster in two), a deep-analysis agent (delta debugging with a skill distilled from human experience, plus dynamic debugging with a source-level debugger on a debug build), and a rules-synthesis agent. Dispositions: known issue, new bug, or false positive; each must meet evidence criteria audited by the coordinator.
- **Two feedback channels (§5.3):** a dialect false positive yields an *adapter rule* that rewrites the request (statements, graph construction, expected errors, or rejecting unsupported shapes) while preserving the testing intent; a confirmed bug family or duplicate yields a *gate rule* (with positive and negative cases) in the issue library, so later reports with the same root cause are filtered.
- **Plan-aware triage (§5.4):** for each equivalence pair, obtain both plans with `EXPLAIN` and compare their hashes. Same plan on the same graph state: dropped without executing either query. Different plans, same result: kept with execution times as a possible performance issue. Different plans, different results: candidate logic bug.

**Insight.** In semantic regions where systems may validly differ, disagreement between systems is weak bug evidence, while one system contradicting itself across equivalent forms is strong evidence (§1, G2). An equivalence-based metamorphic pair that compiles to the same plan on the same graph state returns identical results by construction, so it cannot reveal a defect; if that shared plan is buggy, both queries are wrong in the same way and the oracle stays silent (§1, §2.3, §4.4).

**Findings.**
- Finding 1: twelve hours per method and database on Neo4j, Memgraph and FalkorDB produce 4,114 raw reports, of which 3,136 (76.2%) are false positives; GDsmith alone produces 1,439 false positives in 1,584 reports, and GraspDB's 40 reports on Neo4j and 35 on FalkorDB are all false positives (§4.2, Table 2).
- Finding 2: reports of real bugs are dominated by duplicates: GraphGenie's 527 reports on FalkorDB are 249 false positives and 278 reports of a single bug; Gamera's 234 on Memgraph are 123 false positives and 111 reports of one bug (§4.2).
- Findings 3–4: overlooked graph-semantic constraints cause false positives in five of the eight methods, over half of those from Gamera (75.6%), Dinkel (56.2%) and GDsmith (51.1%); eight Cypher systems make five different combinations of legality, multiplicity and reset boundary (Tables 3, 4). Example (Fig. 2): on one node with one self-loop, `MATCH (n0:L1)-[:T4]-()-[:T4]-() RETURN 1 AS a7` returns 1 row on FalkorDB (edge reuse allowed) and 0 on Neo4j (not allowed); both are valid. Dialect example (Fig. 1a): `MATCH (a)-[r]->(b) WITH * RETURN a, b` is accepted by Neo4j and rejected by FalkorDB, which needs `WITH a, r, b`.
- Finding 5: one system contradicting itself is a real bug: FalkorDB returns 2 rows for the exact-length form of a two-hop pattern but 5 for the explicit and split forms, while Neo4j and Memgraph return 2 on all three (Fig. 4).
- Finding 6: 5–34% of comparable equivalence pairs compile to the same plan (Table 5; 5,000 pairs per run, three seeds, within 1.3 points): GraphGenie 11.29 / 15.34 / 18.94%, GRev 13.71 / 5.79 / 19.76%, GraspDB 5.50 / 26.67 / 33.24%, Dinkel 27.44 / 17.44 / 34.21% on Neo4j / Memgraph / FalkorDB. Of 54 equivalence-preserving transformations on Neo4j, 33 never collapse (Fig. 5). Collapse comes from rule-based rewriting (reversing `(a:A)-[:R]->(b:B)` and adding `WHERE true` gives the same operator tree on any data, Fig. 6) and from cost-based optimization (reordered comma patterns anchored at the rarest label, Fig. 7).
- Finding 7: net-zero writes (e.g. `CREATE (c0 {id:-1}) DELETE c0`) resist collapse, since the optimizer keeps the Create, Delete and Eager operators (Fig. 8).

**Results.** On NeuG 0.1.1, a recently open-sourced industrial graph database (Alibaba GraphScope team) not covered by prior graph-database testing work:
- 19 previously unknown unique bugs; all 19 reported, all 19 confirmed by the developers, 13 already fixed (§6.4).
- Per method (Fig. 10): GDsmith 2, GraphGenie 3, GRev 2, GraspDB 4, Dinkel 9, Gamera 2, GSlicer 3, GDBMeter 3; sets overlap, so no single method finds all 19 and none more than half; each method was run until its count stopped growing.
- Workload reduction on three batches (Table 6): Batch #1 26 raw → 13 after the gate → 3 clusters → 4 analysis units → 2 adapter rules, 1 gate spec, 1 bug family (84.6%); Batch #2 17 → 13 → 3 → 3 → 1, 2, 0 (82.4%); Batch #3 12 → 9 → 3 → 4 → 1, 2, 1 (66.7%).
- Human audit of 100 analyzed reports (Table 7a): 91% agreement with human verdicts, real-bug recall 29/29 (100%), false-positive recall 62/71 (87.3%); the 29 bug reports collapse to 3 unique bugs. Audit of 100 reports filtered by the issue gate (Table 7b): all 100 duplicates, 0 new bugs.

Limits stated (§7): every bug count rests on human judgment (two-author protocol); eight methods over four Cypher systems, so results may not transfer to other query languages; the fixed 12-hour budget changes report volumes; plan collapse is measured by within-system plan-hash comparison and can only be undercounted; the false-positive cause analysis is qualitative.
